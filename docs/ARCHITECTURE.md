# Architecture notes

## Clocks

| Clock | Frequency | Source | Drives |
|---|---|---|---|
| `clk_74a` | 74.25 MHz | Pocket | APF bridge, ROM loading, DIP registers, I2S MCLK |
| `clk_sys` | 24.75 MHz | `dl_pll` (VCO 742.5 MHz / 30) | Z80, AY, LD-V1000, scoreboard |
| `clk_vid` | 6.1875 MHz | `dl_pll` (VCO / 120) | video timing and rendering |
| `clk_vid_90` | 6.1875 MHz, +90° | `dl_pll` | Pocket scaler sample clock |

Clock enables in `dlair_top.v` use fractional accumulators to hit exact
averages: 4 MHz for the Z80, 2 MHz for the AY, 1 MHz for the LD-V1000 timers.

Video is 394 × 262 clocks per field at 6.1875 MHz = 59.94 Hz, 320 × 240
active. The LD-V1000 is locked to the video: each field start crosses into
`clk_sys` and drives the player's per-field logic, just as a real player is
locked to the disc's field rate.

## Game board (`dlair_board.v`)

From MAME `dlair.cpp`, `dlus_map`:

| Address | Dir | Function |
|---|---|---|
| 0000-9FFF | R | program ROM (Rev F2 uses 0000-7FFF) |
| A000-A7FF | RW | RAM, mirrored to BFFF |
| C000 | R | AY-3-8910 data |
| C008 | R | P1: up, down, left, right, action (active low) |
| C010 | R | SYSTEM: start1, start2, coin1, coin2, b6 LD status strobe, b7 LD command strobe |
| C020 | R | LD-V1000 status byte |
| E000 | W | AY data |
| E008 | W | misc: b4 coin counter, b5 push LD data on falling edge, b6 LD enter |
| E010 | W | AY address |
| E020 | W | LD data latch |
| E030-E037 | W | LED digits 8-15 |
| E038-E03F | W | LED digits 0-7 |

All I/O addresses mirror with mask 1FC7 (A5-A3 select the register).
IRQ is 16 MHz / 8 / 16⁴ = 30.5 Hz, held until the Z80 acknowledges it.
DIP banks A and B are read through the AY's I/O ports.

Scoreboard digits: 0-5 player 1 score, 6 player 1 lives, 7 player 2 lives,
8-13 player 2 score, 14-15 credits. Codes 0-9 and A-E map through MAME's
`led_map`; F is blank.

## LD-V1000 (`ldv1000_hle.v`)

The board writes a byte to the E020 latch and pulses E008 bit 5. The player
handles it as a key press:

- A command is only taken while status bit 7 (ready) is set. Taking it
  clears ready; a **no-entry** (`FF`) sets it again. This is why the game
  sends `FF` between every key.
- Digits build a frame number; `SEARCH` (`F7`), `AUTOSTOP` (`F3`) or a timed
  `STOP` (`FB`) consume it.

Strobes, as in MAME: while the disc spins, one status strobe (SYSTEM bit 6
low for 26 µs) and one command strobe (bit 7 high for 25 µs, 54 µs later)
per field, 500 µs into the field. Parked: the same pair every 21 ms.

Status codes: `7C` park, `64` play, `65` still, `50` searching, `D0` search
finished, `54` autostop, `4C` scan, `2E` forward at a set speed; bit 7 is
the ready bit.

Seek time: MAME's slider halves the distance every field, so the emulation
lands after about log2(distance) + 2 fields.

**Deviations from MAME's HLE**

- `AUTOSTOP` plays on and stops at the target frame (MAME only sets the
  status).
- `SKIP FORWARD n` jumps n × 10 frames and keeps playing (MAME treats it as a
  slow seek).

Dragon's Lair may not use either; if a later game does, these follow the
real player's documented behaviour rather than MAME's placeholder.

**Known gap:** MAME's HLE reports `D0` as soon as the game sends `FF` after a
search, before the seek lands. MAME runs Rev F2 with that behaviour, so it is
kept here. If attract mode on hardware plays the wrong scene right after a
search, holding status at `50` until the seek completes is the first thing to
try (one line in the `CMD_NOENTRY` case).

## Video (`ld_testvideo.v`)

Milestone 1 stand-in. Values cross from `clk_sys` once per field through a
toggle handshake (`dlair_top.v`) so the renderer always sees one consistent
snapshot. The overlay text is generated by `tools/gen_overlay.py`; edit the
`LAYOUT` table there and re-run it rather than editing `dl_text.v`.

## Milestone 2 plan: disc video from SD

Source material: Hypseus/Daphne `.m2v` (MPEG-2 video), `.ogg` (audio) and
`.txt` framefile that maps disc frame numbers to file offsets.

The Pocket has no hardware video decoder and MPEG-2 in fabric is out of reach,
so a PC-side converter will re-encode the disc into a format the FPGA can
display directly, and the core will stream it from SD with APF target
data-slot reads (deferred-load slot).

Budget, as plain arithmetic at 29.97 frames/s:

| Format | Bytes/frame | Data rate |
|---|---|---|
| 320×240, 4 bpp (16-colour palette per frame) | 38,400 + palette | ~1.15 MB/s |
| 320×240, 8 bpp | 76,800 | ~2.3 MB/s |
| 160×120, 8 bpp, doubled on output | 19,200 | ~575 KB/s |
| 320×240, 8 bpp + simple RLE | varies (cel art compresses well) | below 8 bpp raw |

Questions to answer on hardware before committing to a format:

1. Sustained throughput of target data-slot reads from SD on the Pocket.
2. Seek latency for a random read (sets how much of the disc must sit in
   SDRAM/PSRAM vs. stream on demand). The Pocket has 64 MB SDRAM and
   2 × 16 MB PSRAM.
3. Whether the converted disc fits in RAM outright at the chosen format, which
   would make seeks free.

Converter (to write): decode `.m2v` with ffmpeg, index frames through the
framefile, quantise per-frame palettes, write one container file with a frame
index table, and resample the `.ogg` to 16-bit PCM in the same container.
